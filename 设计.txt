检视完现在三个仓库的实际状态后，我认为**以前的总方向不需要推翻，但版本路线需要明显调整**。

最重要的变化是：

> **旧规划里 Agent Runtime v0.2 之后直接进入 v0.3 Learning，现在不应该这么走。**
>
> 应该先插入一整层 **Capability Acquisition / Capability Fabric**。
>
> 因为一个真正的数字生命，在“从经验中学习”之前，首先应该具备一个更基础的能力：
>
> **知道自己会什么 → 知道自己不会什么 → 找到别人已经拥有的能力 → 判断能不能信 → 获得/调用能力 → 验证 → 纳入自己的能力模型。**

而且现在的代码基础实际上已经非常适合这样演进，不需要推倒重来。

# 一、我对当前代码状态的结论

### 1. `v0.2.1-embodiment` 应该正式冻结，不要继续往里面塞 Capability

现在 Runtime 已经明确了自己的定位：

- v0.1：Self Continuity
- v0.2：Sensory / Regulatory / Survival
- v0.2.1：Environment / Embodiment
- VirtualBrain 是可插拔 MotivationEngine
- Network 是可选社会层
- v0.3 Learning 暂时冻结，等当前接口稳定。

而 `fa6e3f1` 又进一步把 Contract 1.0 的规则钉死了：

> root shape 不再变化，兼容演进只能进 `extensions`；改变 root 字段或语义必须升 Contract 2.0。

这个决定非常正确。

**不要因为今天讨论 Capability 又去修改 Contract v1。**

---

### 2. 当前最先需要完成的，不是 Capability，而是 VirtualBrain Contract Sync

`cd1f53a` 已经把这件事情写得非常明确：

> VirtualBrain Phase 3 先只同步 `fa6e3f1` 的 Contract，不碰 SA 理论模型；完成之后 Phase 3 冻结，再进入 Life Loop Integration。

而我检查了目前 VirtualBrain 的 `contract_v1.py`，它确实还是旧结构：

- `SelfStateView` 仍输出 `identity`
- `capability_estimates` 还在 root
- `WorldStateView` 没有 `extensions`
- `OutcomeView` 仍然把 `latency/reward/capability/...` 放 root。

所以：

**这一步必须先完成。**

---

### 3. Capability 其实早就在你的设计里，只是过去没有成为主线

这是这次检视最有意思的地方。

Runtime 的 `SelfModel` 已经有：

```python
capabilities: dict[str, CapabilityBelief]
```

而且默认知道：

```text
observe
introspect
maintain
diagnose
llm_provider
```

并且已经支持 `capabilities.xxx` 的 SelfModel update。

`CapabilityBelief` 也已经包含：

```text
available
proficiency
uncertainty
evidence_refs
```



旧设计甚至已经写过：

```text
agent.capability.acquired
agent.capability.retired
```

以及 SA-03：

> 禁用某个 tool → Agent 发现能力缺失 → 更新 SelfModel → 重新规划。

SA-06 也明确包含：

> capability gap → endogenous goal。 

所以今天不是突然改方向。

而是：

> **把以前散落在 SelfModel、Learning、Network、SA Benchmark 中的 capability 概念，提升为正式基础设施。**

# 二、新的总架构：Capability Fabric 不要做第四个产品

我不建议现在创建：

```text
capability-fabric/
```

第四个仓库。

先保持三个项目：

```text
VirtualBrain
     │
     │ motivation / self-awareness research
     ▼
Agent Runtime
     │
     │ optional social capability source
     ▼
Agent Network
```

而 Capability Fabric 是：

> **横跨三个系统的一种协议思想，但核心实现属于 Runtime。**

职责应该变成：

```text
┌──────────────────────────────────────┐
│            VirtualBrain              │
│                                      │
│ 我相信自己会什么？                    │
│ 我是否意识到自己能力不足？             │
│ 能力缺口是否产生探索/求助/学习动机？    │
└───────────────────┬──────────────────┘
                    │
                    ▼
┌──────────────────────────────────────┐
│            Agent Runtime             │
│                                      │
│ Capability Need                      │
│ Capability Gap                       │
│ Resolver                             │
│ Evaluator                            │
│ Acquisition                          │
│ Verification                         │
│ Activation                           │
│ Usage / Learning                     │
└───────────────────┬──────────────────┘
                    │
        ┌───────────┼─────────────┐
        ▼           ▼             ▼
      Local      Public         Network
      Skill      Ecosystem      Agents
      Tool       GitHub         A2A
      MCP        PyPI/npm       Evidence
```

也就是说：

### VirtualBrain

研究：

> “主体什么时候意识到自己不会？”

而不是负责：

> `pip install xxx`

### Agent Runtime

负责：

> “发现缺能力以后，怎么真正获得能力。”

### Agent Network

负责：

> “社会中谁声称拥有这个能力，有什么历史 Evidence？”

而不是替 Runtime 决定：

> “应该安装什么。”

# 三、最关键的新 Runtime 闭环

现在 Runtime 大体是：

现在的 `SimplePlanner` 仍然直接从 Goal/Motivation 产生 `ActionProposal`，还没有“执行这个计划需要什么能力”的概念。

```text
       ▼

       │
       ├── Local
       ├── Agent Network
       ├── Agent Skills

       ├── Packages
       └── GitHub
       │
       ▼
 Capability Evaluator
       │
       ▼

       │

       ├── ACQUIRE
       ├── ADAPT

       │
       ▼

       │
       ▼

       │
       ▼

       │
       ▼

       │
       ▼

```

这就是我认为 Digital Life Runtime 的第一个真正重要的“学习外界能力”闭环。

# 四、最重要的规则：CREATE 必须从默认行为降为最后选择

这应该成为 Runtime 的架构规则，而不是 Prompt。

正常 coding agent 是：

```text
任务
 ↓
设计
 ↓
写代码
```

你的 Runtime 应该强制：

```text
任务
 ↓
需要哪些 capability？
 ↓
已有？
 ↓
别人有？
 ↓
能调用？
 ↓
能安装？
 ↓
能复用？
 ↓
能适配？
 ↓
都不行
 ↓
CREATE
```

因此：

```python
CapabilityDecision.action
```

我建议固定为：

```text
REUSE_LOCAL
DELEGATE_REMOTE
ACQUIRE
ADAPT
CREATE
```

而不是简单：

```text
found / not found
```

所以以后 Runtime 内部可以统一表示，但**外部协议尽量复用标准**。

# 七、核心对象怎么定义

## `CapabilityNeed`

表示：

> “我现在缺什么。”

例如：

```python
@dataclass
class CapabilityNeed:
    capability_id: str
    intent: str

    required_inputs: dict
    required_outputs: dict

    constraints: dict

    max_side_effect: str
    required_permissions: set[str]

    urgency: float
    evidence_refs: list[str]
```

例如：

```text
capability_id:
    software.rate_limit

intent:
    provide distributed API rate limiting

constraints:
    language=python
    license=MIT|Apache
    maintained=true
```

# 十、CapabilityInventory 与 SelfModel 必须分开

这是一个重要设计。

现在：

```python
SelfModel.capabilities
```

表示的是：

> **“我认为自己会什么。”**

它不应该变成 package manager。

新增：

```text
CapabilityInventory
```

表示实际 Runtime 层：

```text
安装了什么
连接了什么
当前版本
由谁提供
是否健康
怎么执行
```

例如：

```text
CapabilityInventory

twitter.search
    kind = TOOL
    provider = Agent-Reach
    state = ACTIVE

software.review
    kind = REMOTE_AGENT
    provider = agent://bug-review-agent
    state = AVAILABLE

pdf-processing
    kind = AGENT_SKILL
    provider = agentskills
    state = ACTIVE
```

然后：

```text
Inventory = 实际情况

SelfModel = 对实际情况的认知
```

这与你一直强调的：

> Self ≠ World

其实完全是一脉相承的。

# 十一、还要区分“我的能力”和“我可以调用的能力”

比如：

```text
bug-review-agent
```

在 Network 里。

我可以调用它。

但不能说：

> “我会代码审查。”

应该区分：

```text
OWNED
LOCAL
REMOTE_ACCESS
ACQUIRABLE
UNAVAILABLE
```

否则数字生命会形成错误 Self Model。

这一点对于 VirtualBrain 的 SA-03 特别重要。

# 十二、Agent-Reach 应该怎么接

不要 fork 它，也不要复制它里面的 Twitter/Reddit 实现。

Agent-Reach 已经在做：

> 稳定 capability surface + 多 backend + install/configure + doctor。

比如 backend 失效后可以换后端，用户无需理解底层实现；并且已经有 `doctor` 做健康诊断。

所以直接实现：

```text
AgentReachCapabilityProvider
```

暴露例如：

```text
web.read
web.search

youtube.search
youtube.transcript

github.read
github.search

twitter.read
twitter.search

reddit.search
...
```

健康检测：

```text
agent-reach doctor
```

Runtime 关心：

```text
youtube.transcript = HEALTHY
```

不关心：

```text
底下到底是 yt-dlp
还是 bili-cli
还是其他工具
```

这正是你应该借鉴的抽象。

# 十四、Agency Agents 要特别处理

这个项目不能直接：

```text
install = 成为这个人格
```

因为你的 Agent Runtime 有：

```text
persistent identity
SelfModel
continuity
```

而 Agency Agents 中很多资产包含：

- personality
- communication style
- role identity
- mission
- workflows。

因此应该把它们拆成：

```text
Expertise Profile
Workflow
Procedural Knowledge
```

而默认丢弃：

```text
You are XXX
Your identity is XXX
You must always behave as XXX
```

也就是说：

> **能力可以学习，人格不能被一个安装包随便覆盖。**

这一条要写成 Runtime invariant。

# 十五、安全必须从第一版就进入 Capability Acquisition

否则“数字生命主动学习”很快就会变成：

> 自动从 GitHub 下载随机项目并执行 shell。

所以生命周期至少：

```text
DISCOVERED
 ↓
INSPECTED
 ↓
APPROVED
 ↓
ACQUIRED
 ↓
VERIFIED
 ↓
ACTIVE
 ↓
DEGRADED
 ↓
QUARANTINED / RETIRED
```

而：

```text
DISCOVERED != SAFE
ACQUIRED != TRUSTED
POPULAR != TRUSTED
NETWORK_TRUST != LOCAL_AUTHORIZATION
```

尤其 Agent Network 当前 Trust 模型本身已经明确：

> Seed 不是 Trust Source；Trust 来自 Evidence；v0.3 `(agent_id + capability)` 的 experience counts 也不是 capability score。

这个原则应该延续到 Runtime。

# 十六、Capability Policy

不要把所有东西粗暴塞进 `AutonomyPolicy`。

新增：

```python
CapabilityPolicy
```

但它必须服从现有：

```text
Constitution
Operator Authorization
AutonomyPolicy
ResourceBudget
```

现有 `AutonomyPolicy` 已经有 allowed actions/resources、compute/financial ceiling、network/deployment restrictions 和 human approval。

增加：

```yaml
capabilities:

  reuse_before_create: true

  allowed_sources:
    - local
    - agent_network
    - agent_skills
    - mcp_registry
    - github
    - pypi

  allowed_kinds:
    - SKILL
    - TOOL
    - MCP
    - REMOTE_AGENT
    - LIBRARY

  license_allowlist:
    - MIT
    - Apache-2.0
    - BSD-3-Clause

  sandbox_required: true

  auto_acquire:
    read_only_skill: true
    executable_code: false
    system_package: false

  require_human_approval:
    - secret_access
    - financial_side_effect
    - deployment
    - system_package
    - irreversible_action
```

# 三十二、给后续所有实现 LLM 的总指令

这段建议以后放进三个仓库的架构规划中：

```text
CAPABILITY FABRIC IMPLEMENTATION RULES

目标：
让数字主体具备发现、获得、验证、使用和积累外部能力的能力，
而不是默认自己重新实现所有功能。

架构边界：

1. VirtualBrain 研究主体如何感知能力边界、形成探索/求助/学习动机。
2. Agent Runtime 负责 Capability 的 discovery、resolution、acquisition、
   verification、activation、usage 和 persistence。
3. Agent Network 负责远程 Agent capability discovery、Evidence、
   verification history 和 trust projection。
4. 不创建第四个 Capability Fabric 产品，除非未来出现两个以上
   与 Runtime 无关的独立 consumer，需要抽离中立协议。

协议规则：

5. Contract v1 root shape 已冻结，不得为 Capability 修改 Contract v1。
6. Agent Skills 使用现有 Agent Skills specification。
7. MCP 使用官方 MCP Registry。
8. Remote Agent capability 优先兼容 A2A AgentSkill。
9. 不创建新的通用 Skill 标准、MCP Registry 或 Agent capability protocol，
   除非现有标准确实无法表达需求。

Capability 决策顺序：

10. REUSE_LOCAL
11. DELEGATE_REMOTE
12. ACQUIRE
13. ADAPT
14. CREATE

15. CREATE 是最后选项。
16. 创造 reusable capability 前必须有 CapabilityDecision 和搜索证据。
17. GitHub stars 不得直接作为 trust 或 quality。
18. Network trust 不等于 Runtime authorization。

安全：

19. 不自动执行任意 GitHub repository。
20. 不自动执行未经检查的 Skill scripts。
21. Executable capability 必须经历：
    INSPECT → POLICY → SANDBOX → VERIFY → ACTIVATE。
22. Capability 不能突破 AutonomyPolicy、Constitution、ResourceBudget。
23. Survival 或 capability need 不能提升 operator authorization ceiling。
24. Secrets 不进入 Runtime snapshot、Network Evidence 或 Skill memory。
25. 外部 Agent/persona 不得覆盖 persistent identity 或 SelfModel identity。

Self Model：

26. CapabilityInventory 表示客观可执行/可访问能力。
27. SelfModel.capabilities 表示主体对自身能力的 belief。
28. LOCAL/OWNED/REMOTE_ACCESS/ACQUIRABLE 必须语义区分。
29. 外部 capability claim 不得直接变成高 proficiency。
30. proficiency/confidence 必须逐渐由真实使用 Evidence 更新。

Persistence：

31. 新增持久字段必须向后兼容 v0.2.1 snapshot。
32. dataclass 新字段必须提供 default/default_factory 或提供 migration。
33. 不移动已有持久 dataclass 的 module path，除非有 migration。

实施顺序：

34. 先完成 VirtualBrain fa6e3f1 Contract Sync。
35. 冻结 Agent Runtime v0.2.1。
36. 实现 v0.2.2 Capability Foundation。
37. 实现 v0.2.3 Resolver / Reuse Before Create。
38. 实现 v0.2.4 Acquisition / Verification。
39. 实现 v0.2.5 Network / Capability Autonomy。
40. 然后才进入 v0.3 Learning。
41. v0.4 Evolution。
42. v0.5 Reproduction。

禁止为了 Capability 解冻 Agent Network Trust Foundation v0.2。
```

---

我认为这个调整非常关键，因为它会改变你这几个项目的性质。

以前的路线是：

> **一个 Agent 如何自己越来越复杂。**

现在增加 Capability Fabric 后，路线变成：

> **一个数字主体如何生活在一个已经存在大量知识、工具、Agent、Skill 和软件的世界里，并像人一样学会利用文明积累。**

这两者差别非常大。

而且它把你最开始提出的“AI 写代码不要重复造轮子”，和更长期的“真实数字生命”连接起来了：

**不重复造轮子只是表象；真正的基础能力是——认识自己的能力边界，并从世界中获得能力。**
